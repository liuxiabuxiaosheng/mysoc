## 项目事实摘要

- 项目定位：使用 SystemVerilog 设计并仿真验证一套面向 FPGA 原型的 RISC V Audio DSP SoC。

## 30 秒项目介绍

我用 SystemVerilog 设计并仿真验证了一套 RISC V Audio DSP SoC。系统包含多周期 RV32IM、64 KiB BRAM、APB 外设、DMA、中断控制器，以及跨 50 MHz 系统域和 12.5 MHz 音频域的异步 FIFO 与 16 阶 Q1.15 FIR。项目重点是把 CPU 控制、数据搬运、CDC 和定点运算串成可验证的数据链路。目前 36 个自检 Testbench 全部通过，项目结论以 RTL 仿真为边界。

## 2 分钟项目介绍

这个项目是一套面向 FPGA 原型的 RISC V Audio DSP SoC。我先搭建片上存储和 APB 外设平台，再实现多周期 RV32IM 内核，让 CPU 能通过统一请求响应接口访问 64 KiB BRAM 和 GPIO、Timer、UART、DMA、音频控制及中断控制器。处理器支持 RV32I 基本指令、RV32M 乘除法、Machine CSR、异常和中断返回。

音频链路的目标是减少 CPU 逐样本搬运。我实现了单通道 DMA 和 CPU 与 DMA 的 BRAM 仲裁，DMA 可以完成 BRAM 到 BRAM、BRAM 到音频输入 FIFO，以及音频输出 FIFO 到 BRAM 的搬运。系统域和音频域之间通过参数化异步 FIFO 传递 16 位样本，音频域内使用 16 阶 Q1.15 FIR，支持舍入、饱和和 valid-ready 反压。仿真中完成了 50 MHz 到 12.5 MHz 双时钟链路以及 40 个样本的逐样本黄金模型比对。

我认为项目中最需要推敲的部分是 APB 等待时序、异步 FIFO 满空判断、复位后的跨域状态，以及定点 FIR 的位宽和反压。验证上采用从单元、接口到 SoC 的自检 Testbench，目前 36 个测试全部通过。I2S RX、TX 和桥接也有独立仿真，但真实 Codec、Vivado 实现和板级时序还没有闭环，所以我不会把这些部分描述为已经完成。

## Q02 SoC 的整体架构和一笔音频数据的完整流向是什么

**面试官提问**

请从控制流和数据流两个角度描述系统架构。

**项目化参考回答**

控制流由多周期 RV32IM 发起。CPU 通过统一请求响应总线访问 BRAM，或经 CPU 到 APB Bridge 访问外设寄存器。APB Interconnect 根据 4 KiB 地址窗口选择 GPIO、Timer、UART、Audio CTRL、DMA 或 IRQ Controller。数据流中，CPU 先在 BRAM 准备输入并配置 DMA。DMA 每次从 BRAM 读取一个 32 位 word，拆成两个 16 位样本写入音频输入 FIFO。样本跨到音频域后进入 FIR，输出再经异步 FIFO 回到系统域，DMA 将两个 16 位样本合成一个 32 位 word 写回 BRAM。

### 追问 1

**追问问题**

为什么 CPU 不直接逐样本读写 FIR？

**追问参考回答**

逐样本搬运会让 CPU 长时间轮询 FIFO 状态并承担跨域节拍，控制开销与音频数据量线性增长。DMA 把规则搬运从软件移到硬件，CPU 只需配置源地址、目的地址和长度，再通过状态或中断获知完成，更符合 SoC 中控制面与数据面的分工。

### 追问 2

**追问问题**

当前链路中的长度单位是什么，有什么约束？

**追问参考回答**

DMA 的长度按 32 位 word 计数。BRAM 到音频输入时，一个 word 拆为低 16 位和高 16 位两个样本；音频输出到 BRAM 时，两个样本重新拼为一个 word。因此输入样本数需要是偶数，地址还必须 4 字节对齐。

**回答要点**

- 清楚区分 CPU 控制路径和 DMA 音频数据路径。
- 说明 32 位存储接口与 16 位样本之间的打包关系。

## Q03 为什么采用多周期 CPU 而不是流水线 CPU

**面试官提问**

多周期设计性能较低，你为什么还这样选？

**项目化参考回答**

这个项目的目标是先建立可解释、可验证的 SoC 控制核心，而不是追求最高 IPC。多周期结构把取指、译码、执行、访存和写回分成明确状态，可以复用 ALU 和单端口式请求响应接口，也避免数据冒险、控制冒险、前递和冲刷流水线的额外复杂度。对校招项目而言，它便于我完整实现 RV32IM、CSR、Trap 和外设访问，并把主要精力放在总线、DMA、CDC 和 DSP 的系统集成上。代价是每条指令需要多个周期，乘除法和存储等待会进一步增加延迟。

### 追问 1

**追问问题**

多周期 CPU 的 CPI 是固定的吗？

**追问参考回答**

不是。普通 ALU 指令大致经历 FETCH、DECODE、EXECUTE、WRITEBACK；Load 和 Store 还要进入 MEMORY，并受总线 ready 延迟影响；RV32M 指令进入 MEXT_WAIT，除法是迭代实现；WFI 可能停留到中断条件出现。因此 CPI 与指令类型和从设备等待有关。

### 追问 2

**追问问题**

后续升级为流水线时最先遇到什么问题？

**追问参考回答**

首先要处理寄存器相关、分支跳转和异常精确性，其次要定义取指与数据访问能否并行。如果仍共享一条存储通路，还会出现结构冒险。CSR、Trap 和中断需要明确在哪一级提交，保证异常之前的指令完成、之后的指令不产生可见副作用。

**回答要点**

- 选择理由应与项目目标和验证复杂度对应。
- 不要把“简单”说成没有代价，要主动说明吞吐限制。

# 第二轮 总线外设与存储系统

## Q04 APB 传输的 Setup 和 Access 阶段如何实现

**面试官提问**

结合你的 CPU 到 APB Bridge 说明一次传输时序。

**项目化参考回答**

Bridge 在 IDLE 看到 `req_valid` 后锁存地址、读写方向、写数据和字节使能，进入 SETUP。SETUP 周期拉高 `PSEL`、保持 `PENABLE` 为 0。下一周期进入 ACCESS，同时保持 `PSEL` 并拉高 `PENABLE`。如果 `PREADY` 为 0，状态留在 ACCESS，地址和控制信号由锁存寄存器保持稳定；看到 `PREADY` 后采样 `PRDATA` 和 `PSLVERR`，进入 RESP，在 CPU 侧给出一个周期的 `resp_ready` 和错误标志。

### 追问 1

**追问问题**

为什么请求信号必须锁存，不能直接接 CPU 输入？

**追问参考回答**

APB Access 阶段可能被 `PREADY` 拉长，协议要求地址、方向和写数据在等待期间保持不变。如果直接使用 CPU 输入，而 CPU 在请求之后改变信号，就会破坏从设备看到的传输。锁存把一次事务的控制信息固定到响应结束。

### 追问 2

**追问问题**

这个 Bridge 支持多个 outstanding 请求吗？

**追问参考回答**

不支持。它从 IDLE 接收一个请求，到 RESP 返回后才重新接收下一笔，是单 outstanding 设计。优点是状态和错误对应关系简单，缺点是不能并发隐藏 APB 延迟。对当前多周期 CPU 和低带宽配置外设足够。

**回答要点**

- 准确说出 `PSEL`、`PENABLE` 和 `PREADY` 的周期关系。
- 等待状态下稳定性来自请求寄存器，不来自上游假设。

## Q05 APB Interconnect 如何完成地址译码和错误响应

**面试官提问**

你的 APB Interconnect 如何选从设备，未映射地址怎样处理？

**项目化参考回答**

Interconnect 使用地址 `[31:12]` 做 4 KiB 窗口译码。GPIO、Timer、UART、Audio CTRL、DMA 和 IRQ Controller 分别映射到 `0x4000_0000`、`0x4000_1000`、`0x4000_2000`、`0x4000_3000`、`0x4000_5000` 和 `0x4000_7000`。只有总 `PSEL` 与对应窗口同时命中时才拉高该从设备的 `PSEL`。返回路径按同一译码选择 `PRDATA`、`PREADY` 和 `PSLVERR`。若主设备选中但没有任何窗口命中，互连立即返回 `0xDEAD_BEEF`、`PREADY=1` 和 `PSLVERR=1`，避免总线永久等待。

### 追问 1

**追问问题**

如果两个地址窗口重叠会发生什么？

**追问参考回答**

当前 RTL 用优先级 `if else` 选择返回数据，但多个从设备的 `PSEL` 可能同时拉高，这属于设计错误。更稳妥的做法是在 elaboration 或断言中检查窗口互斥，并对 one-hot 选择做 assertion，不能依赖 MUX 优先级掩盖冲突。

### 追问 2

**追问问题**

从设备内部非法 offset 与未映射地址有什么区别？

**追问参考回答**

未映射地址由 Interconnect 发现，表示没有任何从设备窗口命中；内部非法 offset 是已经选中某个 4 KiB 窗口，但寄存器偏移不存在，由具体从设备返回 `PSLVERR`。两者最终都转成 CPU 侧 bus error，但定位层级不同。

**回答要点**

- 说清窗口译码和从设备内部 offset 校验是两层检查。
- 主动指出地址窗口互斥应由断言或静态检查保证。

## Q06 UART 的收发状态机和 FIFO 如何配合

**面试官提问**

说明 UART TX、RX、FIFO 和 APB 寄存器之间的数据流。

**项目化参考回答**

APB 写 UART DATA 时，如果 TX 已使能且 TX FIFO 未满，低 8 位进入深度 16 的同步 FIFO。TX 空闲时取出一个字节，按空闲高电平、1 位起始位、8 位低位先发数据和 1 位停止位发送。RX 输入先经过两级同步，再检测下降沿；状态机在起始位中点确认低电平，之后按整 bit 周期采样 8 位和停止位。有效字节写入 RX FIFO，停止位不为高会置 frame error。APB 读 DATA 会触发同步 FIFO 读，因此寄存器接口插入一个等待周期后返回数据。RX 非空、帧错误或溢出可以产生可屏蔽中断。

### 追问 1

**追问问题**

为什么在起始位中间再次采样？

**追问参考回答**

检测到下降沿时可能正处在边沿附近，也可能是短毛刺。等待半个 bit 周期后仍为低，能确认有效起始位，并把后续整 bit 间隔的采样点放在每个数据位中间，增加对相位误差的容限。

### 追问 2

**追问问题**

当前 UART 接收方案还有什么局限？

**追问参考回答**

它是单点采样，没有常见的 8 倍或 16 倍过采样、多数表决和更强的抗抖动能力；波特率由整数分频给出，也会有量化误差。当前 Testbench 验证了协议功能和错误状态，但真实串口的时钟偏差、噪声和板级电气条件还需要进一步验证。

**回答要点**

- 说明 RX 两级同步只降低亚稳态传播风险，不等于完整抗噪设计。
- 解释 APB 读等待与同步 FIFO 输出时序的因果关系。

## Q07 Timer 和 IRQ Controller 为什么使用粘滞状态与写一清零

**面试官提问**

为什么中断状态不能只做一个周期脉冲？

**项目化参考回答**

CPU 可能正在执行其他指令、关闭全局中断或服务更高优先级事件，一个周期脉冲容易被错过。Timer 到达 compare 后把状态位置 1，并直接形成 timer IRQ；IRQ Controller 也把 Timer、DMA 和 UART 源锁存在 pending 位中。软件读取原因并处理设备后，再向 clear 寄存器写 1 清除对应位。这样事件从发生到软件确认之间不会丢失。

### 追问 1

**追问问题**

清零与新事件同一周期发生时应该谁优先？

**追问参考回答**

项目中的 IRQ Controller 先执行写一清零，再对有效源逐位置 1，所以同周期新事件优先，pending 保持为 1。这能避免软件清除旧事件时把刚到的新事件一起抹掉。Timer 也应检查同周期 compare 命中与清零的优先关系。

### 追问 2

**追问问题**

电平中断清 pending 后为什么可能马上又置位？

**追问参考回答**

如果底层源条件仍然为真，例如 UART RX FIFO 仍非空，IRQ Controller 下一周期会再次采样到源并置 pending。正确顺序通常是先消除设备侧原因，例如读空 RX 数据或清 sticky error，再清控制器 pending。

**回答要点**

- 粘滞位解决事件与软件响应不同步的问题。
- 写一清零要说明同周期置位优先级和源条件清除顺序。

## Q08 片上 BRAM 如何支持字节半字和整字访问

**面试官提问**

你的 RAM 是 32 位接口，CPU 怎样完成 SB、SH、SW？

**项目化参考回答**

`onchip_ram` 以 32 位 word 数组实现，容量参数默认 65536 字节，地址 `[15:2]` 选择 word。写入时使用 4 位 `req_wstrb` 独立控制四个 byte lane。CPU 对 SB 根据地址低两位生成 one-hot strobe，并把 8 位数据移到对应 lane；SH 根据地址 bit 1 选择低半字或高半字；SW 使用 `4'b1111`。Load 统一读取 32 位 word，再在 CPU 中按地址偏移右移，并对 LB、LH 做符号扩展，对 LBU、LHU 做零扩展。

### 追问 1

**追问问题**

为什么 RAM 模块仍拒绝非 4 字节对齐地址？

**追问参考回答**

当前 CPU 会在发请求前把有效地址和 byte strobe 组织好，但 RAM 接口本身按 word 地址工作，项目的总线约定要求传入 RAM 的请求地址 4 字节对齐。更通用的实现可以让总线保留原始 byte 地址，由 RAM 内部用低位选择 byte lane；当前设计把部分对齐处理放在 CPU 侧，因此接口约束需要明确。

### 追问 2

**追问问题**

怎样让综合工具推断真正的 FPGA BRAM？

**追问参考回答**

需要遵循目标工具支持的同步读写模板，避免不受支持的复位整块存储操作，并检查综合报告中的 RAM 推断结果。初始化文件可通过 `$readmemh` 支持仿真和部分 FPGA 初始化流程，但最终仍要用 Vivado 综合报告确认是 BRAM 还是 LUT RAM，当前仿真通过不能代替该证据。

**回答要点**

- 区分 byte enable、地址偏移和读后扩展三件事。
- 不要仅凭 RTL 数组写法声称已经推断成物理 BRAM。

## Q09 CPU 总线到 APB Bridge 如何处理等待和错误

**面试官提问**

CPU 发起访问后，Decoder 和 Bridge 如何保证请求只完成一次？

**项目化参考回答**

CPU Bus Decoder 在 IDLE 锁存一笔请求，根据地址进入 RAM_WAIT 或 APB_WAIT，并持续向目标端保持 `req_valid`，直到看到目标 `resp_ready`。随后它锁存返回数据和错误，进入 RESP，只在该状态向 CPU 给出一个周期的完成信号。APB Bridge 内部同样从 SETUP、ACCESS 到 RESP 串行推进。因此从 CPU 看每笔事务只有一次明确响应，等待期间地址和控制保持不变。

### 追问 1

**追问问题**

地址空间怎样区分 RAM、APB 和非法区域？

**追问参考回答**

`0x0000_0000` 到 `0x0000_FFFF` 进入 RAM，`0x4000_0000` 及以上进入 APB，二者之间的区域直接返回错误。Decoder 还检查传入请求的 word 对齐。进入 APB 后，未命中具体窗口的访问再由 Interconnect 返回 `PSLVERR`。

### 追问 2

**追问问题**

当前接口为什么叫单 outstanding？怎样扩展吞吐？

**追问参考回答**

因为 Decoder 和 Bridge 都只有一套请求寄存器，在前一笔 RESP 结束前不接收下一笔。要提高吞吐，可以增加请求和响应队列、给事务分配 ID，或换成支持流水传输的总线协议。但 APB 本身适合低带宽寄存器访问，当前设计优先保证简单和可验证。

**回答要点**

- 把等待保持、响应脉冲和错误透传串起来说明。
- 不要把 APB 描述成支持多 outstanding 的高吞吐总线。

# 第三轮 CPU CSR Trap 与中断

## Q10 RV32IM 多周期控制器如何组织状态和数据通路

**面试官提问**

请说明一条 ALU 指令和一条 Load 指令分别经过哪些状态。

**项目化参考回答**

控制状态集中在 `riscv_core`。普通 ALU 指令经过 FETCH、DECODE、EXECUTE 和 WRITEBACK：FETCH 等待指令总线响应，DECODE 产生控制信号，EXECUTE 计算结果并锁存目的寄存器，WRITEBACK 写寄存器并更新 PC。Load 在 EXECUTE 计算有效地址、访问尺寸和符号属性，再进入 MEMORY 等待总线；返回后按 byte offset 截取并符号或零扩展，最后 WRITEBACK。Store 也进入 MEMORY，但完成后直接回 FETCH。RV32M 进入 MEXT_WAIT，WFI 进入单独等待状态。

### 追问 1

**追问问题**

寄存器堆的 x0 怎样保持为零？

**追问参考回答**

写回逻辑应禁止对地址 0 的写入，读取地址 0 时直接返回 0。即使内部数组的第 0 项受到未知值影响，架构可见结果也必须为零。Testbench 会覆盖尝试写 x0 后再次读取的场景。

### 追问 2

**追问问题**

控制器为什么没有单独复杂的 `riscv_control` 实现？

**追问参考回答**

当前项目把核心状态迁移和数据寄存器控制集中在 `riscv_core`，`riscv_control` 只是预留边界。这减少了早期跨模块控制信号数量，但也让 core 文件职责较重。后续若扩展流水线或更多特权功能，我会把状态控制、提交和异常仲裁拆成清晰模块。

**回答要点**

- 用具体状态说明不同指令路径，而不是只背五阶段名称。
- 能诚实说明当前模块边界的优点与技术债务。

## Q11 分支跳转和非对齐访问如何处理

**面试官提问**

分支、JAL、JALR 和访存对齐分别怎样实现？

**项目化参考回答**

条件分支在 EXECUTE 比较两个源寄存器，根据 B 类立即数选择 `PC+imm_b` 或 `PC+4`，有符号和无符号比较分别使用 signed 或普通比较。JAL 把 `PC+4` 写入 rd，并跳到 `PC+imm_j`；JALR 写回 `PC+4`，目标是 `rs1+imm_i` 且最低位清零。访存时，byte 不要求额外对齐，halfword 检查地址 bit 0，word 检查低两位。非对齐访问在配置了 `mtvec` 时进入 Trap，否则进入兼容旧测试的 fault 状态。

### 追问 1

**追问问题**

为什么 JALR 要把最低位清零？

**追问参考回答**

这是 RISC V 规范对 JALR 目标地址的定义，可以允许函数指针最低位携带辅助信息，同时保证目标至少按 2 字节边界对齐。当前内核没有压缩指令，但仍按规范清零 bit 0。

### 追问 2

**追问问题**

能否用两次对齐访问支持非对齐 word？

**追问参考回答**

可以，但要跨两个 word 读取后拼接，Store 还可能需要两次带不同 strobe 的写入，并处理第二笔访问报错时的部分更新问题。当前项目选择直接 Trap 或 fault，逻辑更简单，也便于验证精确异常边界。

**回答要点**

- 分支比较要区分 signed 和 unsigned。
- 非对齐支持不是免费功能，要说明跨边界和部分写风险。

## Q12 CSR Trap MRET 和 WFI 的执行路径是什么

**面试官提问**

发生异常或中断时，CSR 和 PC 怎样变化？

**项目化参考回答**

CSR 模块实现 `mstatus`、`mie`、`mtvec`、`mscratch`、`mepc`、`mcause`、`mtval`、`mip`、`cycle` 和 `time`。Trap 发生时，core 提供原因、PC 和附加值，CSR 保存到 `mcause`、`mepc`、`mtval`，把当前 `mstatus.MIE` 保存到 MPIE，再清 MIE，PC 跳到 Direct 模式的 `mtvec`。执行 MRET 时，PC 恢复为 `mepc`，MIE 从 MPIE 恢复。WFI 进入等待状态，当已使能的中断源出现时返回 FETCH，随后由正常中断判断决定是否进入 Trap。

### 追问 1

**追问问题**

异常和中断在 `mcause` 中怎样区分？

**追问参考回答**

中断把 `mcause` 最高位置 1，低位写入原因码；同步异常最高位为 0。项目中 Machine Timer Interrupt 使用原因 7，Machine External Interrupt 使用 11，非法指令为 2，断点为 3，Load 和 Store 地址错误或访问错误使用相应异常码。

### 追问 2

**追问问题**

为什么项目保留 `mtvec==0` 时进入 halted 的行为？

**追问参考回答**

这是为了兼容早期没有 CSR 和 Trap 时的故障测试。如果没有配置 Trap 入口，非法指令、非对齐或总线错误仍输出 `fault_code` 并停止；配置了 `mtvec` 后才走异常保存和跳转路径。工程上这是一种向后兼容选择，但完整实现最终应统一到规范化的 Trap 语义。

**回答要点**

- 按进入 Trap、保存状态、跳转、MRET 恢复的顺序回答。
- 明确当前只实现 Machine 模式和 Direct `mtvec`。

## Q13 Timer DMA UART 中断如何进入 CPU

**面试官提问**

从外设事件到 CPU 跳转，中间经过哪些使能和 pending？

**项目化参考回答**

Timer 状态进入 IRQ Controller 的 bit 0，DMA 的 done 或 error 进入 bit 1，UART 的 RX 非空或错误中断进入 bit 2。控制器把源锁存为 pending，并用 enable 寄存器屏蔽。Timer pending 形成 CPU 的 timer IRQ，DMA 和 UART pending 合并为 external IRQ。进入 core 后还要满足 `mstatus.MIE` 和 `mie.MTIE` 或 `mie.MEIE`。满足条件时，CPU 保存 `mepc`、`mcause` 和 `mtval`，清全局中断使能并跳到 `mtvec`。

### 追问 1

**追问问题**

Timer 和 External 同时到达时谁优先？

**追问参考回答**

当前 `trap_pending` 同时检测两者，生成 cause 时先判断 Timer，所以 Timer 优先。这个优先级来自 RTL 表达式，不是完整 PLIC 的可编程优先级。面试中我会明确这是当前简化设计的固定优先规则。

### 追问 2

**追问问题**

这个 IRQ Controller 和 PLIC 有什么差距？

**追问参考回答**

当前只有三个源、enable、pending、clear 和固定汇聚，没有源优先级、claim/complete、阈值、多 hart 路由或大量外部源管理。它能验证基本 Machine External Interrupt 路径，但不能等同于完整 PLIC。

**回答要点**

- 区分设备侧状态、IRQ Controller pending、CSR 使能三层门控。
- 不要把简化控制器包装成标准 PLIC 或 CLINT。

## Q14 RV32M 乘除法如何实现特殊边界条件

**面试官提问**

乘法和除法分别怎样实现，除零和溢出怎么处理？

**项目化参考回答**

乘法使用扩展后的 64 位乘积，根据 MUL、MULH、MULHSU 和 MULHU 选择低 32 位或高 32 位，并正确处理 signed 与 unsigned 组合。除法使用 32 次迭代状态机，core 发出 start 后进入 MEXT_WAIT，等 done 再写回。按 RISC V 语义，DIV 或 DIVU 除零返回 `0xFFFF_FFFF`，REM 或 REMU 除零返回被除数；有符号 `INT_MIN / -1` 返回 `INT_MIN`，余数返回 0。

### 追问 1

**追问问题**

为什么除法不用 SystemVerilog 的 `/` 直接写？

**追问参考回答**

直接使用 `/` 便于仿真，但综合后可能得到面积较大或时序不可控的组合除法器，也无法清楚展示多周期握手。迭代除法把面积和延迟的权衡显式化，代价是约 32 个计算周期，需要 busy、done 和 core 等待状态。

### 追问 2

**追问问题**

怎样验证 MULH 系列最容易出错的符号问题？

**追问参考回答**

要覆盖正正、正负、负正、负负、0、1、-1、最大正数和最小负数，并为 MULH、MULHSU、MULHU 分别用 64 位软件表达式生成黄金值。重点检查操作数扩展发生在乘法前，而不是先做 32 位乘法再错误解释高位。

**回答要点**

- 能准确给出 RISC V 对除零和 `INT_MIN/-1` 的规定。
- 说明迭代实现是面积与延迟权衡，不笼统称为性能更好。

# 第四轮 DMA 仲裁与数据搬运

## Q15 DMA 的寄存器状态机和错误处理如何设计

**面试官提问**

请说明 DMA 的配置寄存器、三种模式和主要状态。

**项目化参考回答**

DMA 通过 APB 配置 SRC、DST、LENGTH、CTRL 和 STATUS。LENGTH 按 32 位 word 计数。根据源和目的地址识别三种模式：BRAM 到 BRAM、BRAM 到音频输入端点、音频输出端点到 BRAM。BRAM 模式经过 READ_REQ、READ_WAIT、WRITE_REQ、WRITE_WAIT；输入模式读出一个 word 后用 IN_PUSH_LO 和 IN_PUSH_HI 发送两个样本；输出模式用 OUT_POP_LO 和 OUT_POP_HI 收集两个样本再写一个 word。零长度、地址不对齐、非法端点组合或 busy 时重复 start 会置 config error，存储响应错误置 bus error，完成进入 DONE 并置 sticky done，三类状态都可触发 IRQ。

### 追问 1

**追问问题**

为什么 REQ 和 WAIT 都保持 `mem_req_valid`？

**追问参考回答**

存储接口采用请求保持到响应的约定。第一周期进入 REQ 发起请求，如果 `mem_resp_ready` 没有返回，就进入 WAIT 并继续保持地址、方向和数据，直到响应到达。这样不会把等待误认为请求取消，也不会重复递增地址。

### 追问 2

**追问问题**

DMA 出错后怎样让软件区分原因？

**追问参考回答**

STATUS 分别保留 busy、done、config error 和 bus error。软件读取后可以判断是配置问题还是存储访问问题，再通过对应写一清零位清状态。当前设计没有记录出错地址和剩余长度，后续可增加 fault address 和 residual count 提高可诊断性。

**回答要点**

- 状态机回答要结合三种数据路径，而不是只背 IDLE 到 DONE。
- 主动说明 sticky 状态和诊断信息的当前边界。

## Q16 CPU 与 DMA 访问 BRAM 时如何仲裁

**面试官提问**

CPU 和 DMA 同时请求 RAM 时怎样避免冲突？

**项目化参考回答**

顶层通过仲裁逻辑保证同一时刻只有一个 master 驱动 RAM 请求。DMA 进行搬运时持有访问权，CPU 对 RAM 的访问需要等待；返回数据和 ready 只路由给当前获权 master。这样实现简单，也能保证 DMA 状态机的请求和响应严格配对。代价是 DMA 长传输期间 CPU 访问片上 RAM 的最坏等待时间较大，当前项目更重视正确性而不是公平性和实时性。

### 追问 1

**追问问题**

固定优先级可能带来什么问题？

**追问参考回答**

如果 DMA 连续占用且没有传输间隙，CPU 可能长时间得不到 RAM，影响取指或数据访问，严重时表现为饥饿。改进方式包括 word 级轮转、突发长度限制、时间片、CPU 紧急优先级，或者使用真正双口 BRAM 把取指和 DMA 数据访问分开。

### 追问 2

**追问问题**

怎样验证仲裁没有把响应送错 master？

**追问参考回答**

Testbench 应让 CPU 和 DMA 在相邻或同一周期请求，随机拉长 RAM 响应，并记录获权者。断言可以检查任何周期只有一个 RAM 请求源生效、等待期间 grant 不变、每个 response 必须对应此前的请求，而且未获权 master 不能看到 ready。

**回答要点**

- 解释请求选择和响应路由必须使用同一事务归属。
- 能指出固定优先级的饥饿风险及可实施的改进。

# 第五轮 CDC 与异步 FIFO

## Q17 为什么多比特数据跨时钟域要使用异步 FIFO

**面试官提问**

为什么不能给 16 位音频数据每一位都加两级同步器？

**项目化参考回答**

两级同步器适合缓慢变化的单比特电平，作用是降低亚稳态传播概率。对 16 位总线分别同步，每一位的解析时间可能不同，接收端可能看到来自两个样本的混合值，而且没有事件计数和流量控制。异步 FIFO 在写时钟域把完整样本写入双口存储，只跨域同步 Gray 编码的读写指针；接收端根据本地域的 empty 判断何时读取，从而保持数据原子性、顺序和速率解耦。

### 追问 1

**追问问题**

异步 FIFO 是否消除了亚稳态？

**追问参考回答**

没有。指针跨域的第一级同步触发器仍可能进入亚稳态，设计只是通过两级同步降低亚稳态传播到功能逻辑的概率，并用 Gray 编码限制相邻指针只变化一位，减少采到不一致多比特值的风险。最终可靠性还要结合器件参数、目标频率和 MTBF 分析。

### 追问 2

**追问问题**

为什么数据存储本身不需要逐位同步？

**追问参考回答**

写端只在本地时钟写当前地址，读端只有在同步后的指针表明非空后才访问相应地址。指针同步延迟为存储内容提供稳定时间，读写由不同地址和双口存储语义隔离。实现到 FPGA 时仍要确认工具对双口 RAM 和跨时钟读写的推断与约束。

### 追问 3

**追问问题**

单比特脉冲跨域还可以怎样做？

**追问参考回答**

如果脉冲可能短于目标时钟周期，直接两级同步可能漏掉。可以把脉冲转换为电平握手，或使用 toggle synchronizer，在源域翻转状态、目标域同步后检测变化；如果事件可能连续到达并需要计数，异步 FIFO 或跨域计数器更合适。

**回答要点**

- 两级同步器降低风险但不保证多比特一致性。
- 解释 FIFO 通过存储和指针协议保证样本原子性。

## Q18 Gray 指针异步 FIFO 如何判断满空

**面试官提问**

请结合 next pointer 说明 empty 和 full 的判断公式。

**项目化参考回答**

本项目保留 `ADDR_WIDTH+1` 位二进制读写指针，最高位用于区分是否绕回，并用 `gray=(bin>>1)^bin` 转换。写域把读 Gray 指针两级同步后，用下一写 Gray 指针与处理后的同步读指针比较：一般深度下翻转读指针最高两位，其余位保持，匹配时表示下一次写会追上读指针，即 full。读域把写 Gray 指针两级同步后，用下一读 Gray 指针直接比较，同值表示 empty。用 next pointer 计算可以让状态在本次成功读写后及时更新。

### 追问 1

**追问问题**

为什么 full 比较要翻转最高两位？

**追问参考回答**

二进制环形指针满条件是写指针与读指针低地址相同，但绕回相位相差一圈。转换成 Gray 后，这个相位关系对应最高两位取反而其余位相同。只翻转一位是常见错误，会在部分绕回位置误判。深度 2 的参数化分支需要单独处理。

### 追问 2

**追问问题**

为什么同步后的指针会让 full 或 empty 偏保守？

**追问参考回答**

跨域同步需要两个本地时钟周期，写域看到的读指针可能落后，因此即使读端已经释放空间，full 还可能多保持几拍；读域看到的写指针也可能落后，因此新数据写入后 empty 可能延迟解除。这会降低瞬时吞吐，但不会导致越界读写，属于安全的保守判断。

### 追问 3

**追问问题**

Gray 编码为什么要求相邻值只变化一位？

**追问参考回答**

二进制计数在进位时可能多位同时翻转，目标域若在变化窗口采样，可能组合出相差很远的值。Gray 相邻状态只有一位变化，跨域采样最多面对这一位的新旧不确定，经过同步后不会形成任意多位混合码，从而降低错误满空判断的风险。

**回答要点**

- 满空判断使用的是同步后的对端 Gray 指针和本地 next pointer。
- 接受状态释放延迟以换取不越界的安全性。

## Q19 异步 FIFO 的独立复位有什么风险

**面试官提问**

写域和读域可以独立复位时，为什么容易出现假满、假空或旧数据？

**项目化参考回答**

每个时钟域只直接复位自己的二进制指针、Gray 指针、同步级和状态。若一侧先释放，另一侧仍在复位，本地看到的对端指针会经过同步延迟才一致；若运行中只复位一侧，还可能把指针清零而存储中保留旧数据，使两端对 FIFO 内容的理解不同。项目 Testbench 覆盖独立复位释放，但系统级使用仍应规定复位协议，例如初始化时两侧都复位，并在两侧稳定释放若干周期后才允许业务写读。

### 追问 1

**追问问题**

复位信号跨时钟域应怎样处理？

**追问参考回答**

常见做法是异步拉低、同步释放。异步断言可以立即把逻辑置为安全状态，同步释放避免复位在时钟边沿附近解除导致不同触发器恢复不一致。每个时钟域都需要自己的复位同步器，不能把一个域同步后的复位直接用于另一个域。

### 追问 2

**追问问题**

运行中单边复位后，如何保证重新开始时不消费旧数据？

**追问参考回答**

需要系统级 flush 或重新同步协议，例如停止两侧流量、同时复位两侧指针、等待同步级收敛，再由控制握手宣布 FIFO 可用。仅复位一侧而继续另一侧业务，当前简单 FIFO 无法保证保留或丢弃数据的语义。

### 追问 3

**追问问题**

overflow 和 underflow 为什么做成粘滞标志？

**追问参考回答**

它们表示上游在 full 时仍请求写入，或下游在 empty 时仍请求读取。这类违规可能只出现一个周期，粘滞标志便于软件或 Testbench 在之后检查。项目 FIFO 在本地域复位时清除标志，系统级还会同步部分错误状态到控制域进行计数或报告。

**回答要点**

- 独立复位不只是复位语法问题，还涉及两端数据语义。
- 给出异步断言同步释放和业务使能等待的完整策略。

# 第六轮 FIR 定点音频与 I2S

## Q20 16 阶 Q1.15 FIR 的位宽舍入和饱和如何设计

**面试官提问**

两个 Q1.15 数相乘后是什么格式，16 阶累加为什么使用 40 位？

**项目化参考回答**

16 位 Q1.15 有 1 个符号位和 15 个小数位。两个数相乘得到 32 位有符号乘积，小数位数为 30。16 个乘积累加至少需要额外约 4 位增长，再加符号保护，所以项目使用 40 位累加器留出余量。输出前按 15 位小数位做算术右移，把结果恢复到 Q1.15 标度；正负数分别加或减半个 LSB 实现对称舍入。若缩放结果超过 `0x7FFF` 或低于 `0x8000` 表示的最小负数，就分别饱和到最大正值或最小负值，避免回绕。

### 追问 1

**追问问题**

为什么负数舍入不能和正数完全同样相加？

**追问参考回答**

算术右移对负数通常向负无穷取整。如果简单对所有数都加半个 LSB，会让正负方向的舍入偏差不对称。项目对非负累加值加半 LSB，对负累加值减半 LSB，再算术右移，使远离零方向的半位处理保持对称。具体舍入规则仍应在规格和黄金模型中保持一致。

### 追问 2

**追问问题**

怎样证明 40 位一定够？

**追问参考回答**

可以用最坏情况上界计算：单个 16 乘 16 有符号乘积需要 32 位，16 项同号相加理论上增加 `ceil(log2(16))=4` 位，36 位可覆盖基本幅度；40 位再留保护位。若系数不受 Q1.15 幅值或总和约束，还要按实际系数范围重新计算，不能只凭经验位宽。

### 追问 3

**追问问题**

为什么饱和比直接截断更适合音频？

**追问参考回答**

直接截断溢出会二进制回绕，大正数可能变成负数，产生很强的失真。饱和把结果限制在可表示上下界，虽然也会削顶，但符号和幅度变化更符合音频系统预期。Testbench 应同时覆盖正溢出、负溢出和边界附近不饱和情况。

**回答要点**

- 从 Q 格式、小数位、累加增长、舍入到饱和依次说明。
- 位宽结论要用上界推导和系数约束支撑。

## Q21 FIR 如何处理 valid-ready 反压

**面试官提问**

如果下游 FIFO 满了，FIR 怎样保证输出不丢失、历史样本不多移一次？

**项目化参考回答**

FIR 只有一个输出保持寄存器，`in_ready = !out_valid || out_ready`。当输出无效，或当前输出在本周期被下游接收时，模块可以接受新输入；如果 `out_valid=1` 且 `out_ready=0`，`in_ready` 拉低，输出数据和 valid 保持，同时不接受新样本，也不移动 history。只有 `in_valid && in_ready` 时才进行乘加、更新历史并产生新输出。这样输入样本、历史状态和输出一一对应。

### 追问 1

**追问问题**

同一周期旧输出被接收且新输入到达，会发生什么？

**追问参考回答**

此时 `out_ready=1`，所以 `in_ready=1`。时序块先表示旧输出完成，又因为输入握手成立计算并登记新输出，最终 `out_valid` 继续为 1，输出寄存器换成新结果。这样可以做到每个时钟接受一个样本，没有额外空泡。

### 追问 2

**追问问题**

当前 FIR 真的是 16 个流水级吗？

**追问参考回答**

不是。当前 RTL 在一次输入握手时用循环描述 16 个乘法与加法的组合计算，并在时钟沿登记结果，功能吞吐可以每拍一个样本，但组合路径可能很长、资源可能映射为多个并行乘法器。是否满足目标频率必须由综合和时序报告确认。后续可把乘加树分级流水，或复用一个 MAC 做 16 周期迭代。

### 追问 3

**追问问题**

流水化 FIR 后 valid-ready 最难处理什么？

**追问参考回答**

需要让数据、valid 和每级中间结果一起推进，并定义遇到反压时是整条流水线停顿，还是增加 skid buffer 或弹性寄存器。若只停输出级而前级继续推进，会覆盖未消费结果。还要重新定义总延迟、吞吐和系数更新时机。

**回答要点**

- 反压时不仅保持输出，还必须冻结与该输入对应的历史更新。
- 区分功能上一拍一吞吐与物理时序上已经流水化。

## Q22 I2S RX TX 和音频桥接如何工作

**面试官提问**

说明 I2S 的一位延迟、采样边沿和跨域桥接。

**项目化参考回答**

RX 在 `i2s_bclk` 上升沿工作，检测 LRCLK 变化后记录左右声道，并跳过 I2S 规定的一个 bit offset，再移入 16 位数据，完成时输出 sample valid、data 和 channel；声道提前切换会置 frame error。TX 在 BCLK 下降沿驱动数据，同样在 LRCLK 切换后处理一位延迟，按 MSB first 输出 16 位；没有对应声道样本时输出 0 并置 underrun。桥接模块用两只 16 位异步 FIFO 在 I2S BCLK 域与 audio clock 域之间传样本，并用预取寄存器和 toggle 握手协调 TX 数据装载与消费。

### 追问 1

**追问问题**

为什么 RX 在上升沿采样而 TX 在下降沿更新？

**追问参考回答**

这样 TX 在下降沿改变串行数据，RX 或外部 Codec 可在上升沿附近采样，提供大约半个 BCLK 的建立时间。最终边沿定义必须与所选 Codec 的 I2S 时序数据手册一致，不能只依据通用习惯。

### 追问 2

**追问问题**

为什么 I2S 模块通过独立测试还不能说明真实音频接口可用？

**追问参考回答**

独立仿真验证的是逻辑协议和样本顺序。真实接口还需要确定 Codec 型号、主从模式、BCLK 与 LRCLK 频率、时钟占空比、管脚电压、输入输出延迟、复位和上电配置，并通过 XDC 与静态时序分析验证。板级信号完整性和真实回环也不在当前证据中。

**回答要点**

- 准确说出 I2S LRCLK 切换后的一位延迟和 MSB first。
- 清楚区分模块仿真、跨域桥接验证和物理 Codec 验证。

# 第七轮 验证调试与项目复盘

## Q23 你如何构建自检 Testbench 和黄金模型

**面试官提问**

你的 36 个测试如何分层，怎样判断结果不是只看波形看出来的？

**项目化参考回答**

测试从单元、接口、子系统到 SoC 分层。单元层覆盖 ALU、CSR、乘除法、FIFO、FIR、UART TX/RX 和 I2S；接口层覆盖 RAM、CPU Bus Decoder、APB Bridge、Interconnect 和 DMA；子系统与 SoC 层覆盖 CPU 运行、外设访问、中断、DMA 和音频端到端链路。Testbench 主动驱动事务、等待握手，并用 `if`、`$fatal` 或期望队列自动比较，不依赖人工看波形。FIR 和音频链路在 Testbench 中用更高精度运算复现移位、舍入和饱和规则，逐样本与 RTL 对比。

### 追问 1

**追问问题**

端到端通过是否意味着各模块边界都覆盖充分？

**追问参考回答**

不意味着。端到端测试能证明一条场景贯通，但内部错误可能互相抵消，异常分支也可能没有触发。因此还需要单元测试覆盖满、空、回绕、等待、非法地址、除零、非对齐、反压和独立复位，并用断言检查协议不变量。

### 追问 2

**追问问题**

如果进一步提高验证质量，你会加什么？

**追问参考回答**

我会增加 SystemVerilog Assertions，例如 APB 等待期间地址控制稳定、FIFO 不在 full 时写或 empty 时读、响应必须对应请求；再加入随机等待、随机复位和随机样本序列，收集功能覆盖率。CPU 还可以使用 RISC V 指令参考模型做差分验证，CDC 部分用专门静态 CDC 工具检查同步器和 reconvergence。

**回答要点**

- 说明测试的激励、判定器和失败机制，而不只报测试数量。
- 承认定向 Testbench 与覆盖率、形式验证、CDC 静态检查之间的差距。

## Q24 当前项目最大的不足和下一步改进是什么

**面试官提问**

如果给你两周继续做，优先解决什么，为什么？

**项目化参考回答**

最大的不足是目前证据集中在 RTL 仿真，尚未得到综合后资源、关键路径、CDC 约束和板级音频结果。我的优先顺序是先建立 Vivado 工程和正确 XDC，确认 50 MHz 输入、系统时钟、音频时钟和异步时钟组；然后综合实现，检查 BRAM 与 DSP 推断、FIR 组合路径、跨域同步器标记和时序违例；最后接入明确型号的 Codec，完成 I2S 管脚、时序约束和硬件回环。若时序不满足，再针对 FIR 做流水化、对仲裁和 FIFO 边界做结构调整。

### 追问 1

**追问问题**

你预计最可能的时序瓶颈在哪里？

**追问参考回答**

最可疑的是 FIR 中 16 个乘积和累加的组合路径，其次是较大的控制与返回 MUX。异步 FIFO 的 Gray 指针同步本身不是普通跨域时序路径，应通过正确的异步时钟组和同步器约束处理，但本地域的 full 与 empty 比较仍需要满足时序。最终要以综合和实现报告为准。

### 追问 2

**追问问题**

项目里哪项表述最容易在面试中说过头？

**追问参考回答**

最容易说过头的是把“面向 FPGA 原型”说成“已经上板”，把 RTL 数组说成“已经使用 BRAM”，把一拍接收一个样本说成“FIR 已完成高频流水化”，或把独立 I2S Testbench 说成“真实 Codec 已打通”。我会始终把仿真事实、综合结论和板级结果分开。

**回答要点**

- 下一步顺序应从约束和测量开始，再依据报告优化。
- 用可证据化语言陈述能力，诚实边界本身也是工程素养。
